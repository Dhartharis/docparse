# Operational connection management

This document covers organization-scoped **configuration and credential management**, introduced in PR #8. Signed Push reception and the price/stock projection are implemented separately in the [Push increment](operational-push.md). On-demand Pull is available through the [Admin query preview](operational-live-query.md); synchronization schedules, bot tool access and automatic Debt Assistant onboarding remain pending. A `configured` connection has the required saved fields/keys; it is not a verified provider connection or proof of synchronized data.

Product direction: [DocParse definition](https://docs.google.com/document/d/1ao033DtGdlLEpfZSGLFziUoYwa5ztnBSh7mcjROCITE/edit). Implementation proposals: [design PR #4](https://github.com/Dhartharis/docparse/pull/4) and [wire-contract PR #6](https://github.com/Dhartharis/docparse/pull/6). This feature does not integrate or approve those PRs. Stripe test billing remains independent in [PR #7](https://github.com/Dhartharis/docparse/pull/7).

## Ownership and endpoints

The new Integrations module owns its `integrations` schema, connection definitions and protected credentials. Application records/validation and store ports do not depend on HTTP, Npgsql or Data Protection. Infrastructure implements persistence and encryption. Access is checked through `IOrganizationAccess`; feature code never queries Access's persistence. Tenant foreign keys are part of the additive schema history.

All management routes require current authenticated organization Admin access. Viewers and other organizations receive no connection information. Authenticated management responses use `Cache-Control: no-store`; newly issued secrets are never returned to an unauthenticated caller.

| Route under `/api/organizations/{organizationId}/connections` | Behavior |
| --- | --- |
| `GET /` | List the organization's connection metadata and whether provider origins have been configured; no secret/ciphertext fields |
| `POST /` | Create with a caller request UUID and validated definition; identical request replay recovers the same identity without showing its original secret again |
| `PUT /{connectionId}` | Update name, freshness, clock allowance and scheduled interval using the current revision |
| `POST /{connectionId}/push-key` | Rotate the receiving key with explicit expiry and current revision; return the new secret once |
| `PUT /{connectionId}/pull-key` | Store/replace the provider's read credential with current revision; never return its secret |
| `POST /{connectionId}/disconnect` | Disable the connection and revoke/erase stored key material; safe to repeat after disconnection |

Source business, provider base URL and selected modes are immutable after creation. Use a new connection to change the source identity or destination. A definition can enable Push, on-demand Pull and scheduled Pull together, or a subset; at least one is required. Push and Pull credentials are separate and conversation API keys are not accepted as signing secrets.

`revision` is a GUID for configuration concurrency, not a product record's numeric source revision from the wire contract. Every successful settings/key mutation changes it. A stale update returns `409 connection_conflict`; refresh rather than silently overwriting another administrator's work. Disconnecting an already disabled row is idempotent and never restores credentials. Replaying an old create request cannot reactivate that row.

## Keys and security

Receiving keys use independent random 32-byte secrets, encoded as 64 lowercase hexadecimal characters, and unique key identifiers. The Admin selects a lifetime of 1-365 days. The server returns a newly issued secret only on creation/rotation. After an uncertain response, an identical create replay returns metadata with a null secret; inspect the existing connection and explicitly rotate if the original secret was not saved. Concurrent creates with the same request ID issue only one connection/key. The same request ID with a different normalized definition is an integrity conflict.

Provider credentials are entered as a provider-issued key ID and 64 hexadecimal characters; uppercase is normalized. They are not generated by DocParse or assumed to authorize another provider business. Replacing the saved credential stops its local use; revocation at the external provider is a separate operator action. The app does not modify that provider.

Secrets are protected using the existing persisted ASP.NET Data Protection key ring, with purposes scoped by organization, connection, direction and key ID. Key-ring file access/protection happens before opening database transactions. Transactions atomically persist/revoke credentials and change connection revisions. One current credential per connection/direction is enforced by a partial unique index. On replacement/disconnect, old metadata is retained but its encrypted secret is erased. Metadata endpoints do not expose active plaintext or ciphertext. The UI retains newly issued secrets only in component memory, supports explicit copy/hide and clears them on close/organization change; no browser storage is used. Keep the persisted Data Protection keys according to the V1 setup; losing that key ring requires credential reissuance.

Connection/credential composite organization foreign keys prevent cross-tenant linkage even if an application check is accidentally bypassed. All credential queries and mutations include both organization and connection. Row locks plus revision checks serialize concurrent changes. Settings ranges and full-string key/identifier validation reject malformed values, including trailing control characters.

## Provider destinations and local setup

Push-only definitions need no provider URL. Pull definitions require a trusted base URL with no embedded credentials, query or fragment. HTTPS is required except explicit loopback/host.docker.internal HTTP in Development. A URL prefix is retained and normalized to a trailing slash.

The deployment operator must approve the provider origin in `Integrations:AllowedProviderOrigins`; the default list is empty. This list is not disclosed as a catalog of other customers' destinations. For the current local Compose configuration, set the ignored `.env` entry:

```text
INTEGRATION_PROVIDER_ORIGIN=https://your-provider.example
```

Or configure multiple origins through environment entries `Integrations__AllowedProviderOrigins__0`, `__1`, etc. Origins contain scheme/host/optional port only; the connection may specify an API path beneath that origin. No credentials belong in a URL or checked-in settings. This setting authorizes configuration only: actual provider calls still require request-time destination/DNS/redirect protection in the Pull implementation, plus provider-side business/scoped credential authorization. Do not treat an allowlisted hostname as proof that its resolved addresses are safe.

Once the feature is integrated, rebuild the local API/migration image, apply migrations, rebuild frontend assets and recreate the API as described in the repository setup. Migration `018_operational_connections.sql` deliberately avoids the `017` filename reserved by the separate Stripe PR; it has no dependency on Billing tables and does not rewrite any existing migration.

## Admin experience

Open **Account -> Data connections**. Create a named source business, choose modes and review the explicit freshness/clock/interval values. The form proposes editable values; the API requires valid values and has no silent missing-field defaults. For Pull, save the provider key separately. Missing/expired credentials appear as `needs_credentials`. New key display is one-time; key replacement and disconnection require an explicit confirmation in the interface. No feature is restricted by a paid plan.

The generic form is intended for technical setup. The later Debt Assistant connection flow must select/authorize the actual Business and exchange scoped credentials, rather than asking end users to copy these generic fields. That delegated identity/authorization protocol remains to be agreed and implemented; this feature does not infer business ownership by email.

```powershell
dotnet build back/DocParse.csproj
python tests/check_backend_boundaries.py
dotnet run --project tests/ConnectionPolicyTests/ConnectionPolicyTests.csproj
npm --prefix front ci
npm --prefix front run build
npm --prefix front run lint
npm --prefix front test -- --workers=4
python tests/connections_integration.py --browser
python tests/backend_integration.py --browser
git diff --check
```

The policy runner needs no extra package, database or provider. PostgreSQL tests use disposable databases/containers with a dedicated temporary image; they verify tenant/Viewer denial, allowed destinations, concurrent/idempotent create, one-time disclosure, protected storage, key rotation/replacement, stale writes, credential foreign keys, expiry, disconnect races, old-request replay and restart persistence. Browser tests cover EN/ES/VI, desktop/mobile and a real API create/edit/rotate/disconnect journey. No source provider is contacted.

The general backend regression suite requires an image built from this branch. To avoid replacing the main app's `docparse-api` tag during review, it can run with a temporary Compose override for the `api` and `migrate` image references. Build a separate image, provide that override through `COMPOSE_FILE`, and retain the existing local PostgreSQL/Azurite/Mailpit services. Do not use the old main image when checking the new migration count.

PR #8's workflow builds/policy-checks only; the later Push workflow also runs its isolated database/browser checks on GitHub. Frontend publication remains manual. When combining with Stripe PR #7, preserve both localization key sets and advance the combined catalog version beyond the highest merged version (Push uses version 4).
